# Feature Specification: LLM 게이트 (Relevance & Landmark Gate — Precision)

**Feature Branch**: `006-llm-relevance-landmark-gate`

**Created**: 2026-06-22

**Status**: Draft (retro-spec — 기존 동작 역기록)

**Input**: L1 §006 retro-spec. 수집(003)→기계필터·dedup(004)이 거른 미본 신규 후보의 초록을
LLM 으로 읽고 2단계(① 관련성 = 대상 P AND 중재 I 동시 매칭 / ② 랜드마크 = practice-changing)로
판정해 사람에게 보낼 가치가 있는 랜드마크만 선별한다. 정밀(precision) 레이어 — 검색 recall
(두-검증 §005)과 별개 층. 운영 백엔드 = 로컬 claude CLI(OAuth·Haiku), 추가비용 0(헌법 III).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관련성 게이트로 토픽-인접 오탐 차단 (Priority: P1)

감시 시스템이 후보 논문의 초록을 읽고, 그 논문이 KQ 의 **대상(P)과 중재(I)를 둘 다** 직접
다루는지 판정한다. 한쪽만 맞으면(대상은 맞지만 다른 중재, 또는 중재는 맞지만 다른 대상)
관련 없음으로 떨어뜨려, 검색이 넓게 긁어온 토픽-인접 오탐을 사람에게 닿기 전에 차단한다.

**Why this priority**: 검색식은 일부러 넓은 그물(§003)이라 후보 다수가 주제만 비슷한 오탐이다.
관련성 차단이 없으면 사람이 받는 알림이 잡음으로 가득 차 감시 자체가 무력해진다. 정밀 레이어의
1차 관문.

**Independent Test**: 대상 불일치(예: '신장이식 수액전략')·중재 불일치(예: '복부수술 로봇 vs
복강경') 사례를 게이트에 넣으면 관련 없음으로 거부되고, 대상·중재 둘 다 맞는 사례는 통과하는지로
단독 검증(`tests/acceptance/gate_baseline.yml` 의 `reject_false_positive` 2건).

**Acceptance Scenarios**:

1. **Given** KQ='복부수술 수액전략' 과 '신장이식 goal-directed fluid' 논문, **When** 게이트 판정,
   **Then** 대상(P) 불일치로 관련 없음(거부)이 되어 랜드마크 평가로 넘어가지 않는다.
2. **Given** 같은 KQ 와 '복부수술 로봇 vs 복강경' 논문, **When** 판정, **Then** 중재(I) 불일치로
   관련 없음(거부)이 된다.
3. **Given** 대상·중재 둘 다 맞는 논문, **When** 판정, **Then** 관련 있음으로 인정되어 랜드마크
   평가 단계로 넘어간다.

---

### User Story 2 - 랜드마크 판정 (practice-changing) + 설계 엄격도 (Priority: P2)

관련 있다고 인정된 논문에 대해, 시스템이 그것이 현행 지침과 *다른 결론·프로토콜*을 제시하는
practice-changing 인지 판정한다. KQ 의 설계 엄격도가 strict 면 질문 유형에 맞는 기대 연구설계
(예: 중재형→RCT) 수준의 근거를 요구하고, loose 면 설계와 무관하게 경계선도 포함한다(놓침이 가장
비싼 오류이므로 recall 편향).

**Why this priority**: 관련성만으로는 "지침을 바꿀 만한 새 근거"인지 알 수 없다. 랜드마크 판정이
사람에게 보낼 최종 가치를 결정한다. 단, 관련성(P1) 차단이 선행되어야 의미가 있다.

**Independent Test**: practice-changing 랜드마크(RELIEF·OPTIMISE)가 랜드마크로 인정되는지
(`gate_baseline.yml` 의 `landmark_true` 2건), 그리고 strict/loose 설정에 따라 경계선 사례의
포함 여부가 달라지는지로 검증.

**Acceptance Scenarios**:

1. **Given** 현행 지침 권고를 뒤집는 관련 논문(예: RELIEF), **When** 판정, **Then** 랜드마크로
   인정되고 한국어 한 줄 사유가 함께 산출된다.
2. **Given** 설계 엄격도 strict 인 KQ 와 기대 설계 미달 근거, **When** 판정, **Then** 랜드마크
   아님으로 판정된다.
3. **Given** 설계 엄격도 loose 인 KQ 와 경계선 근거, **When** 판정, **Then** 포함(랜드마크)
   쪽으로 판정된다(recall 편향).

---

### User Story 3 - 무비용 교체형 백엔드 & 안전한 실패 (Priority: P3)

운영자가 판정 엔진(백엔드)을 sink 처럼 갈아끼울 수 있다 — 개발용(키 불필요)·운영용(로컬 구독
기반, 추가비용 0)·클라우드(과금, 향후). 판정이 실패하거나 응답을 해석할 수 없으면 시스템은
조용히 멈추지 않고 보수적으로 보류(관련 없음 처리)하고 사유를 로그에 남긴다.

**Why this priority**: 무비용·로컬 운영(헌법 III)과 파이프라인 안정성을 보장한다. 단일 판정 실패가
전체 감시 실행을 중단시켜선 안 된다. 기본 동작만으로도 운영 가능하나 백엔드 선택은 튜닝 영역.

**Independent Test**: 운영 백엔드 미연결(개발용 백엔드)에서도 파이프라인이 끝까지 돌고, 판정
응답이 깨졌을 때(파싱 불가) 해당 후보가 보류 처리되며 실행이 계속되는지로 검증.

**Acceptance Scenarios**:

1. **Given** 운영 백엔드(로컬 구독) 선택, **When** 판정, **Then** 추가 API 과금 없이 판정이
   수행된다.
2. **Given** 판정 응답이 깨졌거나 엔진 호출이 실패, **When** 판정, **Then** 해당 후보는 보수적
   보류(관련 없음·랜드마크 아님)로 처리되고 사유가 로그에 남으며 다음 후보로 계속 진행된다.
3. **Given** 판정 엔진이 부가 텍스트로 감싼 응답(래퍼)을 반환, **When** 해석, **Then** 그 안의
   판정 결과를 견고하게 추출한다.

---

### Edge Cases

- 초록이 비어 있거나 매우 짧은 후보? → 가용 정보만으로 판정(제목 기반). 정보 부족 시 보수적 판정.
- 초록이 매우 긴 후보? → 판정 입력은 일정 길이로 절단되어 비용·지연을 제한한다.
- 관련 없음(① 거부)인데 랜드마크처럼 보이는 경우? → 관련성 우선 — ②(랜드마크)는 평가하지 않는다.
- 질문 유형(question_type)이 비어 있거나 모호? → 기대 설계는 일반 적정 설계로 대체. 유형 권위는
  사용자 설정 입력이며 자동 분류는 *보조*(제안·대조 경고)일 뿐 판정을 좌우하지 않는다.
- 운영 백엔드 미구현(클라우드)을 선택? → 경고 후 개발용 백엔드로 안전 강등.
- `[pt]` 등 설계 필터를 검색식에 넣었나? → 금지. 설계는 게이트의 *의미 판단* 컨텍스트일 뿐
  검색식 하드필터가 아니다(헌법 IV·V·IX, 검증 A recall 보호).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 후보의 제목·초록을 입력으로 받아 **2단계**(① 관련성 → ② 랜드마크)로 판정해야
  한다. ②는 ①이 관련 있음일 때만 평가한다.
- **FR-002**: 관련성(①)은 후보가 KQ 의 **대상(P)과 중재(I)를 둘 다** 직접 다룰 때만 인정되어야
  하며, 한쪽만 일치하면 관련 없음으로 거부되어야 한다(토픽-인접 오탐 차단).
- **FR-003**: 랜드마크(②)는 관련 논문이 **현행 지침과 다른 결론·프로토콜의 practice-changing**
  일 때 인정되어야 한다.
- **FR-004**: 설계 엄격도가 **strict** 면 질문 유형별 기대 연구설계 수준의 근거를 요구하고,
  **loose** 면 설계와 무관하게 경계선도 포함해야 한다(loose = recall 편향, 기본값).
- **FR-005**: 게이트는 판정 **컨텍스트**로 KQ 의 대조(C)·결과(O)·지침 라벨·질문 유형·설계
  엄격도와 후보의 제목·초록을 사용해야 한다. 초록은 비용·지연 제한을 위해 절단될 수 있다.
- **FR-006**: 판정 결과는 **관련성·랜드마크 여부와 한국어 한 줄 사유**를 담은 구조로 산출되어야
  한다(acceptance 스키마 `{is_relevant, is_landmark, reason}` 와 정합).
- **FR-007**: 판정 엔진(백엔드)은 **교체 가능**해야 한다 — 개발용(키 불필요)·운영용(로컬 구독
  기반, 추가비용 0)·클라우드(향후 과금). 운영 기본은 로컬 구독 기반 백엔드다.
- **FR-008**: 판정은 **무비용·로컬**(헌법 III)로 수행 가능해야 하며, 유료 API 연결 없이도 운영
  백엔드로 동작해야 한다.
- **FR-009**: 판정 실패·응답 해석 실패 시 시스템은 **보수적 보류**(관련 없음·랜드마크 아님)로
  처리하고 사유를 로그에 남기며, 전체 실행을 **중단하지 않아야** 한다(fail-soft).
- **FR-010**: 판정 엔진 응답이 부가 텍스트/래퍼로 감싸여 와도 그 안의 **판정 결과를 견고하게
  추출**해야 한다.
- **FR-011**: 질문 유형의 권위는 **사용자 설정 입력**이며, 자동 유형 분류는 *보조*(빠뜨렸거나
  모호할 때 제안·대조 경고)로만 동작하고 판정을 좌우하지 않아야 한다.
- **FR-012**: 설계 필터(`[pt]` 등)는 **검색식에 투입 금지** — 설계는 게이트의 의미 판단 컨텍스트로만
  쓰여야 한다(헌법 IV·V·IX, 검증 A recall 보호).

### Key Entities *(include if feature involves data)*

- **판정 결과(Verdict)**: 한 후보에 대한 게이트 산출. 관련성 여부 + 랜드마크 여부 + 한국어 사유.
  스키마 `{is_relevant, is_landmark, reason}`.
- **게이트 컨텍스트(Gate Context)**: 한 KQ 에서 파생한 판정 입력 묶음 — 대조(C)·결과(O)·지침
  라벨·질문 유형·설계 엄격도.
- **판정 백엔드(Backend)**: 교체형 판정 엔진 — 개발용(stub)·운영용(로컬 구독·추가비용 0)·
  클라우드(향후). sink 와 동형의 플러그.
- **질문 유형(Question Type)**: 기대 연구설계를 결정하는 분류(중재·진단·예후·예측). 권위 = 사용자
  입력, 자동 분류 = 보조.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 게이트가 acceptance 참값(`tests/acceptance/gate_baseline.yml`)을 재현한다 —
  랜드마크 기대 **2/2**(RELIEF·OPTIMISE: 관련 있음 + 랜드마크), 오탐 기대 **2/2**(신장이식·로봇
  수술: 관련 없음으로 거부).
- **SC-002**: 운영 시 유료 API 과금이 **0**이다(로컬 구독 기반 백엔드, 헌법 III).
- **SC-003**: 단일 후보 판정 실패가 전체 감시 실행을 중단시키지 **않는다**(fail-soft, 미처리
  예외 0). 실패 후보는 보수적 보류로 처리된다.
- **SC-004**: 백필 실측(2026-06, 96건) 기준 관련성 게이트의 **오탐 통과 0건**을 유지한다.
- **SC-005**: 관련성(①)에서 거부된 후보는 랜드마크(②) 평가 없이 즉시 탈락한다(2단계 순서 보존).

## Assumptions

- 게이트 동작의 등가 기준은 기존 구현이다(`src/alert/llm_gate.py` 의 `judge`/`_claude_cli`/
  `_stub`/`_extract_json`, `src/alert/run.py` 의 게이트 호출·컨텍스트 구성). 재작성 시 동작 보존.
- acceptance 출력 스키마는 `{is_relevant, is_landmark, reason}` (`gate_baseline.yml`·§006). 현행
  코드 내부 키 명명(`relevant` vs `is_relevant`) 정합은 구현(plan) 단계에서 baseline 에 맞춘다.
- 운영 백엔드 = 로컬 claude CLI(OAuth·Haiku). 호출 형식·모델은 구현 세부로 본 스펙 밖.
- 두-검증 채점(§005, recall)·수집(§003)·기계필터·dedup(§004)·알림 fan-out(§007)은 본 피처 밖.
- 자동 질문 유형 분류(`classify_qtype`)는 0단계 보조 도구로 본 피처가 사용하는 컨텍스트 입력의
  *제안자*일 뿐, 판정 권위는 사용자 `key_questions.yml` 입력이다.
- 게이트는 후보 단위로 독립 판정한다(후보 간 상호작용 없음). 비결정성(LLM)은 precision 레이어
  특성으로 수용하며, 결정론 backbone(검색·필터·dedup)과 분리된다(헌법: recall·precision 2층).
- 설계 권위: `.specify/memory/constitution.md`(헌법 III·IV·V·IX·XIII), `system-spec.md` §006.
