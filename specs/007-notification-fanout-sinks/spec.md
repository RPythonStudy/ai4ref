# Feature Specification: Sink 멀티탭 (Notification Fan-out)

**Feature Branch**: `007-notification-fanout-sinks`

**Created**: 2026-06-22

**Status**: Draft (retro-spec — 기존 동작 역기록)

**Input**: L1 §007 retro-spec. 게이트(006)가 선별한 랜드마크를 켜진 모든 출력 통로(sink)로
fan-out 하는 출력 레이어. 모든 통로는 동일 인터페이스('같은 플러그')를 구현하고,
features.yml 토글로 켜진 것만 활성화되며, 키·의존성 부재 시 자동 skip(fail-soft). 한 통로의
실패가 다른 통로·본체 흐름을 막지 않는다. 감시 파이프라인의 마지막 단계(003→004→006→007).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 랜드마크를 켜진 모든 통로로 분배 (Priority: P1)

운영자가 features.yml 에서 원하는 출력 통로(화면·텔레그램·Zotero)를 켜두면, 선별된 랜드마크
1건이 켜진 모든 통로로 동시에 전달된다. 통로마다 같은 내용을 각자의 형식으로 받는다.

**Why this priority**: 아무리 잘 선별해도 사용자에게 닿지 않으면 감시는 무의미하다. fan-out 이
감시 파이프라인의 출력(가치 전달) 그 자체다. 최소한 화면 출력 하나만으로도 동작해야 한다.

**Independent Test**: 통로 2개를 켜고 랜드마크 1건을 흘리면 두 통로 모두 전달 결과(참조)를
반환하는지로 검증. 화면 통로는 의존성 없이 항상 동작.

**Acceptance Scenarios**:

1. **Given** 화면·텔레그램 통로가 켜진 상태, **When** 랜드마크 1건 fan-out, **Then** 두 통로
   모두 전달되고 통로별 전달 결과(참조/식별자)가 반환된다.
2. **Given** 랜드마크 항목(KQ·제목·저널·연도·근거·링크), **When** 화면 통로 렌더, **Then** 사람이
   읽을 형식(제목·메타·한 줄 근거·PubMed 링크)으로 출력되고 내부 전용 필드(초록)는 노출되지 않는다.

---

### User Story 2 - 토글 + 자동 skip (fail-soft) (Priority: P2)

운영자가 통로를 켜뒀더라도 그 통로에 필요한 키·선택 패키지가 없으면, 시스템이 오류로 멈추지
않고 그 통로만 조용히 건너뛰며 사유를 로그에 남긴다. 켜지지 않은 통로는 애초에 활성화되지 않는다.

**Why this priority**: 클론 사용자가 키 없이도 코어(화면 출력)를 쓸 수 있어야 하며, 통로 하나의
설정 누락이 전체를 막아선 안 된다. 다만 P1(전달 자체)이 선행 가치다.

**Independent Test**: 텔레그램을 켜되 토큰을 비워두면 그 통로는 skip 되고, 화면 통로는 정상
전달되는지로 검증.

**Acceptance Scenarios**:

1. **Given** 텔레그램이 켜졌으나 토큰 미설정, **When** 활성 통로 구성, **Then** 텔레그램은
   prereq 미충족으로 skip 되고 사유가 로그에 남으며 나머지 통로는 활성으로 남는다.
2. **Given** features.yml 에서 꺼진 통로, **When** 활성 통로 구성, **Then** 그 통로는 인스턴스화
   되지 않는다.

---

### User Story 3 - 통로 격리 + 영구 보관 + 확장 (Priority: P3)

한 통로가 전송 중 실패해도(네트워크·API 오류) 다른 통로와 다음 항목 처리는 계속된다. Zotero
통로는 랜드마크를 참고문헌함의 지정 컬렉션에 영구 보관하며 한 줄 근거를 메모로 남긴다. 새 통로
추가는 본체(검색·선별)를 건드리지 않고 등록 한 줄로 끝난다.

**Why this priority**: 견고성·보관·확장성은 다수 통로 운영 시 중요하나, 단일 통로 MVP 에는 P1
으로 충분하다.

**Independent Test**: 한 통로가 예외를 던지도록 두고 fan-out 하면 다른 통로 전달이 영향받지
않는지(결과에 실패는 표시되되 흐름은 계속), 그리고 새 통로 클래스를 등록만으로 추가 가능한지로 검증.

**Acceptance Scenarios**:

1. **Given** 통로 A·B 활성, A 가 전송 실패, **When** fan-out, **Then** A 는 실패로 기록(로그·
   결과 None)되고 B 는 정상 전달되며 다음 항목 처리가 계속된다.
2. **Given** 랜드마크와 Zotero 통로, **When** 전달, **Then** 지정 컬렉션(기본 ai4ref-landmarks)에
   서지 항목이 생성되고 한 줄 근거가 메모(Extra)에 보강된다.
3. **Given** 새 출력 통로 구현, **When** 통로 목록에 등록, **Then** 본체(검색·선별·게이트) 코드
   수정 없이 fan-out 대상에 포함된다.

---

### Edge Cases

- 활성 통로가 0개면? → fan-out 은 빈 결과를 반환하고 본체는 정상 종료(경고 로그). 전달처 없음.
- 동일 랜드마크가 이미 보낸 항목이면? → 중복 차단은 본 피처 밖(§004 seen-set). fan-out 은 받은
  항목을 전달만 한다.
- 한 통로가 타임아웃·예외? → 그 통로만 실패 기록, 나머지 통로·다음 항목 계속(격리).
- 링크가 없는 항목? → 식별자(PMID)에서 표준 링크를 자동 생성해 렌더에 포함.
- 안전장치: 실수집인데 게이트가 개발용(stub) 백엔드면 모든 후보가 랜드마크가 되어 스팸 → 외부
  통로(텔레그램 등)는 차단하고 화면 출력만 한다(파이프라인 안전장치, §006/§007 경계에서 보존).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 모든 출력 통로는 **동일 인터페이스**(전달 `send`·가용성 점검 `available`)를 구현해야
  하며, 본체는 통로 종류를 몰라도 동일하게 다룰 수 있어야 한다.
- **FR-002**: 시스템은 features.yml 의 통로별 토글로 **켜진 통로만** 활성화해야 한다.
- **FR-003**: 켜진 통로라도 필요한 키·선택 의존성이 없으면 **자동 skip**(오류 아님)하고 사유를
  로그에 남겨야 한다(fail-soft).
- **FR-004**: 랜드마크 1건을 활성 통로 전체로 **fan-out** 해야 하며, 통로별 전달 결과(참조/
  식별자/None)를 반환해야 한다.
- **FR-005**: 한 통로의 전송 **실패는 격리**되어야 한다 — 로그·결과 None 으로 기록하되 다른 통로와
  다음 항목 처리를 중단시키지 않는다.
- **FR-006**: 화면 출력 통로는 **의존성 0·항상 동작**해야 하며, 사람이 읽을 형식(제목·메타·한 줄
  근거·링크)으로 렌더하고 내부 전용 필드(초록)는 노출하지 않아야 한다.
- **FR-007**: 외부 통로(텔레그램·Zotero 등)의 렌더는 화면 출력 렌더를 **재사용**해 표현 일관성을
  유지해야 한다.
- **FR-008**: Zotero 통로는 랜드마크를 지정 **컬렉션**(기본 ai4ref-landmarks)에 보관하고 한 줄
  근거를 메모(Extra)에 보강해야 한다.
- **FR-009**: 새 통로 추가는 **본체(검색·선별·게이트) 수정 없이** 통로 등록만으로 가능해야 한다
  (플러그 확장, 헌법 VIII).
- **FR-010**: 출력은 **무비용**이어야 한다 — 화면·텔레그램은 표준 기능만, Zotero 선택 의존성은
  지연 로드(미설치 시 skip).
- **FR-011**: 전달 단위는 KQ 라벨·식별자(PMID)·제목·저널·연도·한 줄 근거·링크를 담아야 하며,
  링크는 식별자에서 자동 파생되어야 한다.

### Key Entities *(include if feature involves data)*

- **랜드마크 항목(LandmarkItem)**: fan-out 전달 단위. KQ 라벨·PMID·제목·저널·연도·근거·링크
  (+ 내부 게이트용 초록, 렌더 제외). 키 = `KQ:PMID`(중복 차단 식별자, §004 연계).
- **출력 통로(Sink)**: 동일 플러그 인터페이스(가용성 점검 + 전달). 종류 = 화면·텔레그램·Zotero·
  향후 email 등.
- **멀티탭(Registry/Fan-out)**: 토글로 활성 통로를 구성하고 항목을 전 통로로 분배하는 분배기.
  실패 격리.
- **출력 토글(features.yml notify)**: 통로별 enabled + 통로 옵션(예: Zotero 컬렉션명).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 활성 통로 N개에 랜드마크 1건을 흘리면 N개 통로 모두 전달이 시도되고, 통로별 결과가
  반환된다(기존 `alert.run` fan-out 동작과 등가).
- **SC-002**: 한 통로가 실패해도 나머지 활성 통로의 전달 성공률이 **영향받지 않는다**(격리 — 실패
  통로 외 100% 진행).
- **SC-003**: 키·의존성 없는 클론 환경에서도 화면 출력 통로만으로 감시 출력이 **0개 설정으로
  동작**한다(화면은 항상 가용).
- **SC-004**: 새 통로 1종 추가가 본체(검색·선별·게이트) 코드 **0줄 수정**으로 완료된다(등록 1곳만).
- **SC-005**: 외부 통로 운영에 유료 비용이 **0**이다(표준 기능 + 선택 의존성 지연 로드).

## Assumptions

- fan-out 동작의 등가 기준은 기존 구현이다(`src/notify/base.py`·`registry.py`·`stdout_sink.py`·
  `telegram_sink.py`·`zotero_sink.py`, `src/alert/run.py` 의 `build_sinks`/`fan_out` 호출).
  재작성 시 동작 보존.
- 중복 차단(seen-set)은 본 피처 밖(§004). fan-out 은 받은 랜드마크를 전달만 한다.
- 게이트 판정(§006)·수집(§003)·필터(§004)는 본 피처 밖. 본 피처 = "선별된 랜드마크의 출력 분배".
- 실수집 + 개발용 게이트 백엔드의 외부 통로 차단(스팸 방지) 안전장치는 파이프라인(run.py) 책임으로
  현행 보존한다(§006/§007 경계).
- Zotero linked-file(PDF 첨부) 등 수집 트랙(§011) 연동은 본 피처 밖 — 여기서는 서지 항목 보관까지.
- 외부 서비스(텔레그램 Bot API·Zotero Web API) 가용성·응답 형식은 외부 제약으로 전제한다.
- 설계 권위: `.specify/memory/constitution.md`(헌법 VIII·III), `system-spec.md` §007.
